# D：Agent 与演示讲稿（约5分钟）

## 第1页：Agent自主决策与工具循环（约1分40秒）

我负责的是把数据、检索和模型接成一个可以解释、可以记录的问答流程。这里的
Agent并不是每遇到一个问题就固定查图谱。问题先进入大模型，由模型判断是否需要
图谱证据。需要查询时，它输出query_graph和跳数参数；如果不需要，或者已经查够，
可以选择finish，也可以直接结束路由。代码负责检查参数、执行工具，并把工具结果
交回模型。默认最多查询两次，防止重复查询形成无限循环。

查询工具调用B同学的检索器。它只使用允许的训练图，保留实体ID、关系方向以及
真实路径。工具还返回节点和边的规模，我们另外记录耗时与预算截断。图谱结果经过
候选筛选和证据整理后，进入最终回答阶段。最终结果除了自然语言答案，还包含实体
ID、引用三元组、查询次数、耗时和token用量，便于E同学进行统一评测。

一个重要边界是，Agent只接收Question，不接收带标准答案的QAExample。标准答案、
标准关系路径和预先标注的证据都不进入提示词。推理过程中自己检索出来的图谱证据
可以使用，但不能按标准答案给测试题补候选。日志让我们可以检查实际传给模型的
内容，而不是只看最后一句回答。

## 第2页：三种模式与公平比较（约1分30秒）

三种模式共用同一个大模型和同一份问题。llm模式只给模型题面，不给主题ID、图谱
或候选列表。输出名称在生成以后再映射到实体ID，同名不同ID会保留歧义，不自动
全部算对。text模式加入B的子图，用固定文本规则选择候选和问题相关的真实路径。
gnn模式已经加载C正式发布的两层mean权重，用GAT输出的分数排序候选，并在CPU完成真实推理。

为了控制变量，text和gnn在同一个runner中复用路由和检索结果，使用相同候选集合、
路径准备规则和上下文格式。GNN改变的是候选分数和顺序。证据预算也固定，目前
采用2000个UTF-8字节作为保守上限，这不等于精确2000个token；实际token由API记录。

反向遍历不会被改写成不存在的关系。上下文保存原始三元组，并另外说明走向和反向
标记。模型只能引用实际展示过的证据。这样可以保证引用有来源，但来源真实还不
等于回答在语义上正确，后者仍需要评测。目前已完成200题的真实权重离线契约检查，
以及固定前5题的真实三模式调用；这些开发联调结果还不能当作完整实验结论。

## 第3页：真实演示与结果边界（约1分50秒）

联调中发现，检索召回和模型最终看到的证据之间还有一段损失。B的子图在200道
验证题上覆盖约71.14%的标准答案节点，但最初只有约19.24%进入最终上下文。
原因包括名称重复占用预算，以及默认最短路径有时走了与问题无关的捷径。
我把名称放入共享字典，并在返回子图中选择与问题相关的真实一跳、两跳路径。
保持相同证据预算后，text上下文答案覆盖率达到约46.98%；使用C主配置排序后为
54.99%，两组共享检索与候选路径。这些是离线覆盖诊断，
没有让脚本生成正确答案，也不能把这个数字当作问答准确率。

另外，我用真实DeepSeek跑了24道独立路由题，其中12道需要查询、12道可以跳过。
第一轮有一道题调用了未声明的finish，流程明确报错。随后我把停止动作纳入正式
工具协议并补了回归测试，最终24题都正常完成。这个小集合包含同义问法，只用于
展示查询和跳过决策，不代表通用路由能力，也不混入主QA分数。
